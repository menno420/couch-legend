## Why this file exists

Sessions repeatedly fail to discover what they CAN do (claiming `.mp4`s
unviewable though ffmpeg frame-extraction is standard; forgetting provisioned
env tokens exist) and stall on imagined walls — burning owner attention as
hand reminders. This ledger makes capability knowledge durable across
sessions: one session's discovery is every later session's starting fact.

## Posture decision rule — establish your venue first

- **Owner-live session:** assume NO special limitations apply — act and merge
  directly (superbot Q-0269).
- **Autonomous / routine-fired seat:** pre-route around every known stall
  class recorded below; park only on a REAL denial, never preemptively
  (superbot Q-0270 boot triad: model · venue · ability envelope).

Venue tokens (every entry names where it was verified): `owner-live` ·
`autonomous-project` · `routine-fired` · `subagent` · `any`. Capabilities are
**venue-scoped, not global** — the same operation can work owner-live, be
org-refused on a cross-session binding, and prompt-stall in a plain-started
seat while never prompting in a Routine-spawned one (fleet night review,
2026-07-12). A flat CAN/CANNOT ledger is wrong somewhere by construction.

## THE DISCOVERY RULE

Before declaring anything impossible, and before assuming a tool or
credential is missing:

0. **If the owner stated it, it is already verified — act on it.** *"The token
   is account-scoped." · "You have access to that credential." · "Use this
   provider."* He configured the environment and knows what he enabled. Do not
   probe to check whether he is right, and do not answer his instruction with
   questions about what a credential can or cannot do — **do the thing.**
   Working *is* the verification, which is what step 3 already asks for; failing
   gives you a real error instead of a hypothetical doubt. **This is not an
   exception to verify-first.** That doctrine guards against stale *records* and
   your own *inferences*, and the owner is neither — he is the source a record
   would be describing, so probing his statement first is checking a source
   against its own output. The boundary, and it is the whole boundary: he is
   authoritative on **provisioning**; the **response to a specific call** is
   still read every time, and a real error is still reported verbatim. He is not
   claiming your next request returns 200.
1. **Check this file** — the capability or wall may already be recorded for
   your venue.
2. **Check the environment** — `printenv` / list the available tools BEFORE
   assuming no credentials exist (provisioned env tokens are routinely
   forgotten, not absent).
3. **Attempt once** — try the operation and capture the **exact** error text;
   a guessed wall and a verified wall are different facts.
4. **Append the finding same session** — capability or wall, dated, with the
   venue token, the evidence (exact error, or proof it worked) and the
   workaround if one was found. An unrecorded discovery is re-paid by every
   future session.
5. **Staleness — re-verify what you build on**: an entry older than the
   staleness window (config `cadence.staleness_days`, default 14) that your
   work depends on is a **claim, not a fact** — re-verify it with one cheap
   attempt and append the result. Re-verifications APPEND, never edit: a
   refuted wall can self-resolve platform-side, and a ledger with no
   freshness data is confidently stale — worse than ignorant.

  standing self-merge/owner-gated-merge wall**; do not record one. If a
  *specific* merge/arm call is refused, that refusal is specific to that
  call, venue, and the session's permission mode — note it as a dated,
  verbatim one-off, never generalize it into doctrine. — LAST-VERIFIED: 2026-07-18
- `any` · **GraphQL API quota**: tight — batch queries and prefer the
  REST-backed MCP tools for bulk reads. — LAST-VERIFIED: 2026-07-10

- 2026-08-22 · capability · `any` (remote agent container) · **The per-run debug-key problem is fixable with a COMMITTED keystore, and the APK Sig Block parse works as a CI *assertion*, not just a one-off observation — so signing stability is enforced rather than remembered.** · evidence: (a) the 2026-08-21 three-cert finding **re-verified independently** — a fresh parser written this session reproduced all three recorded fingerprints exactly from the same artifacts (`c31d653` → `f815828465d6ce40…` notBefore 21:25:54Z, `f2a54eb` → `387c7df1bc805a04…` 21:52:14Z, `02e27ca` → `d7f4a2dd77798044…` 22:15:59Z) and **extended the series to a fourth distinct cert**, `43bc128` → `04a12834c0c942ad…` notBefore 22:42:51Z, i.e. four runs four keys, so the effect is a property of the pipeline and not a three-sample coincidence; (b) `keytool -genkeypair -storetype PKCS12 -keyalg RSA -keysize 2048 -sigalg SHA256withRSA -validity 10950 -dname "CN=Android Debug, O=Android, C=US"` mints the conventional debug identity in-session with no Android SDK (JDK's keytool is enough), committed at `android/keystore/debug.keystore` and bound via `signingConfigs.debug` + an explicit `buildTypes.debug`; (c) `tools/check-apk-signer.ts` requires the APK's certificate, the keystore's certificate AND an **independent pin** (`android/keystore/debug-signer-sha256.txt`) to all three agree, and then closes four separate ways an APK can carry the pinned certificate while the DEVICE resolves a different identity: it rejects **duplicate signing-block ids** (Android takes the FIRST match, so a map keyed by id keeps the wrong one), validates **every** identity-bearing scheme block present rather than v2 alone (Android 9+ takes identity from v3), verifies signatures with the public key **inside the pinned certificate** rather than the signer's attacker-controlled declared key, and requires the ordered digest and signature algorithm lists to match (Android rejects a mismatch that verifies fine in isolation). Exactly one signer, exactly one certificate. · **proven to FIRE, with real exit codes read without a pipe**: exit 1 against each of the three pre-change APKs (wrong signer); exit 1 with a distinct "the APK is UNSIGNED" message against a rezipped APK whose signing block was stripped; exit 1 when the keystore is regenerated behind the pin; exit 1 when a **single bit** of the signature is flipped while the certificate bytes stay intact and all three certificate comparisons still pass; exit 1 on an APK carrying the pinned certificate with an impostor RSA-2048 SPKI spliced into the signer's declared-key field (same length, so a byte-for-byte in-place swap); and exit 1 on an APK whose v2 block was duplicated in front of the original. Each bypass was BUILT as a real file and run, not argued. · traps: **a guard that derives its expected value from the artifact it guards checks only same-build consistency** — the first version of this checker read the expected certificate out of the very keystore it was validating, so regenerating the keystore would have moved both sides together and stayed green while every already-installed phone silently lost the ability to update. Caught by Codex (P1 on #14), fixed with the independent pin; the shape generalises to any checker whose baseline lives in the thing being checked. Also: `-sigalg` matters — JDK 21 defaults to SHA384withRSA while Gradle's own debug keys are SHA256withRSA, so pass it explicitly to keep the only changed variable *stability*; and note the cost of the fix, which is real — an APK signed by the new committed key **cannot** install over one signed by an old per-run key, so the transition costs exactly one uninstall (and the save with it, unless `exportCode` is used first).
